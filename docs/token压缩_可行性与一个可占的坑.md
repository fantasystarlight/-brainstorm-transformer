# Token 压缩：先把"能不能省掉训练"这件事测掉

> 承接上一份文档。这次的问题不是"分配算法"，而是：**把连续 m 个 token 压成一个**，
> 让注意力矩阵保持在固定规模以下。先查文献（已有），再实测一个决定性的量（本文贡献）。

## 2. 文献：三条已确立的路线

| 路线 | 代表工作 | 压什么 | 训练成本 |
|---|---|---|---|
| **软提示 / 摘要 token** | [Gist Tokens, NeurIPS 2023](https://papers.neurips.cc/paper_files/paper/2023/file/3d77c6dcc7f143aa2154e7f4d5e22d68-Paper-Conference.pdf) | 把整段提示压成若干 gist token（最高 26×） | 训 gist 嵌入 |
| **逐层激活压缩** | [Activation Beacon, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/fc797c61eb18f7b3ce9a74af0ef0d876-Abstract-Conference.html) | 滑动窗口**逐步**把历史激活压成 beacon | **冻住底座，只训压缩模块** |
| **摘要向量扩上下文** | [AutoCompressors, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.232.pdf) | 学 summary token，把历史折叠进向量 | 训压缩器 |
| **动态预算** | [Global-local adaptive compression, 2026](https://www.sciencedirect.com/science/article/abs/pii/S0025526011965) | 动态决定压什么、压多少 | 视方法 |
| **免训练合并** | [Token Redundancy Reduction, CVPR 2025](https://openaccess.thecvf.com/content/CVPR2025/papers/Kim_Faster_Parameter-Efficient_Tuning_with_Token_Redundancy_Reduction_CVPR_2025_paper.pdf)（ToMe 系） | 按相似度合并 token | 免训练，主要做加速 |

**要点**：你想要的三件事（连续 token 压成一个 / 随 token 变多动态压 / 注意力规模有界）
**分别**都有人做过；"同时做到"的最接近者是 Activation Beacon，
而且它的训练成本是"训一个小模块"，不是"重训模型"。**你不必从零开始。**

**一个值得注意的空白**：这些工作都是**端到端训练**的，因此"块内方差"这个量被编码器
重塑掉了，从来没有单独报出来过。而它恰恰是"能不能免训练压"的判据，也是"该压多狠"的依据。
下面的实测就是在补这个数。

## 3. 压缩在注意力层面到底改了什么（精确形式）

设块 b（连续 m 个 token）内 value 均值为 `v̄_b`，query 行 i 的注意力权重为 `a_ij`：

```
                                    真输出:  Σ_b Σ_{j∈b} a_ij · v_j
                                  压缩后:  Σ_b (Σ_{j∈b} a_ij) · v̄_b
```

两式相减，得到一个**精确**的分解：

```
池化误差 = Σ_b Σ_{j∈b} a_ij · || v_j − v̄_b ||²
```

而 pruning（块内只留最大权重的那个，丢掉其余）的误差是另一种：

```
剪枝误差 = Σ_b [ Σ_{j∈b} a_ij · v_j  −  a_i,best · v_best ]
```

**这两个是不同的损失**，所以"压缩该用平均还是该用挑选"是实测问题，不是可以拍脑袋的。

### 一个重要推论（纠正一个常见直觉）

误差由**块内方差**控制，**不由注意力稀疏度**控制。所以
"注意力很尖，所以可以压"是错的推理：如果尖峰落在块内某个 token 上，
池化会把它和它无差别的邻居平均掉，损失反而更大。
（上一份文档已经实测：注意力确实很尖——IPR 中位数 4.16，熵 2.46 bits，
但这对池化**没有帮助**。）

## 4. 实测（本机，Qwen2.5-Math-1.5B-Instruct，T=512，28层×12头，GQA Hkv=2）

脚本：`probe_token_compression.py` → `docs/token_compression_probe.json`

### 4.1 注意力的尖度（门槛量）

```
有效 key 数 IPR：均值 9.83   中位 4.16   p10 1.41   p90 20.78
注意力熵：      均值 2.46 bits  中位 2.42 bits
```

一行 query 平均只看 ~10 个有效 key（中位 4 个）。所以**边预算侧**的空间确实很大
（与上一份文档一致）。但这不直接等价于"token 可以合并"。

### 4.2 池化 vs 剪枝：同预算下的注意力失真

参照分布 = 真实注意力按块求和（质量守恒）。

| 块大小 m | 压缩率 | 剪枝 TVD | 随机取 TVD | 剪枝保留的质量 |
|---|---|---|---|---|
| 2 | 1/2 | 0.0556 | 0.2133 | 0.880 |
| 4 | 1/4 | 0.0932 | 0.3384 | 0.789 |
| 8 | 1/8 | 0.1209 | 0.4074 | 0.720 |
| 16 | 1/16 | 0.1419 | 0.4372 | 0.661 |

**读法**：
- 剪枝丢掉的是**质量**（块内只留一个 → 丢 12–34% 的注意力质量）。
- 池化在 (query, block) 粒度上**质量守恒**（TVD = 0），
  因为它把块内权重求和后乘块均值——**在"块"这个粒度上是无损的**。
- 但"块粒度无损"是**定义使然**（池化的 (query,block) 分布就是真实分布按块求和），
  不是好消息。真正的问题在 value 侧，见 4.3。

### 4.3 关键实测：块内方差（决定免训练压缩能否成立）

| 块大小 m | 块内均方偏差 / 值的整体尺度 | 注意力加权块内偏差 / 尺度 |
|---|---|---|
| 2 | 0.419 | 0.290 |
| 4 | 0.645 | 0.421 |
| 8 | 0.764 | 0.419 |
| 16 | 0.823 | 0.413 |

**这是全文最重要的数字。**

- 把相邻 **2** 个 token 平均，块内差异已经占总尺度的 **42%**（注意力加权后 29%）。
- 到 m=16 时，块内方差占总方差的 **82%**——也就是**块内方差 ≈ 总方差**，
  意味着"块内那 m 个 token 的 value 几乎和随机取的一样不相似"。

**结论**：在这个模型上，**相邻 token 的 value 表示并不冗余**。
"把连续 token 平均掉"会损失 29–42% 的 value 信号，而且**不随块大小改善**
（注意力加权项在 m≥4 后稳定在 ~0.42）。所以：

> **免训练的均值池化不可行。Token 压缩必须"学"出来。**

这正好解释了为什么 Gist / Activation Beacon / AutoCompressors 全都要训练压缩器：
不是因为工程上偷懒，而是因为**平均本身就会丢失信息**，
训练的目的不是"选择压哪些"，而是**让压缩后的向量承载块内的信息**（而不是块内的均值）。

### 4.4 另一条有用的实测：块内权重分布

```
m=4: 块内权重占比标准差 0.210，最大占比均值 0.294（均匀时是 0.250）
m=8: 块内权重占比标准差 0.135，最大占比均值 0.240（均匀时是 0.125）
```

块内注意力**近乎均匀**（最大占比只比均匀高一点）。这解释了为什么剪枝只丢
12–34% 而不是更多——块内本来就没有一个"特别该留"的 token。
但反过来说：**块内既然近乎均匀，就没有"挑一个代表"的余地**，
必须保留块内的聚合信息 → 再次指向"必须学"。

## 5. "块内方差"作为设计量：一个具体的、还没被占的坑

上面 4.3 的表显示块内方差**随层/头而变**（我这里是全模型平均）。
文献里所有人都是用**固定**的压缩率或固定块大小，然后把压缩率当超参调。

**可做的提案**：把"块内方差"当成**可测的分配信号**——

1. **验证**：块内方差（4.3 的量）是否预测"该层/该头压缩后的质量损失"？
   做法：固定总压缩率，用两种分配——(a) 均匀分配到所有层头，
   (b) 按块内方差从小到大分配（方差小的多压）。比下游任务准确率。
2. **若成立**：这就是一个**免训练的离线规划器**——先用一次前向测出每层每头的块内方差，
   再决定压缩预算怎么分，不需要训练就能比均匀压缩好。
3. **若不成立**：那也是结论——说明块内方差不是瓶颈，得换信号（例如块内方差的方向结构）。

**为什么这个坑值得占**：
- 便宜：一次前向 + 排序，不需要训练（第 2 步）。
- 有明确的判决实验和失败条件。
- 与已有工作不冲突：他们训压缩器，这个提案是**决定压缩器在哪用力**。
- 本机可行：4080 上 1.5B 模型，一次前向几秒。

**必须做的负对照**：随机分配压缩预算（同样总压缩率）。
如果"按块内方差分配"打不过随机分配，提案就是假的。

## 6. 反例清单（这条路上看着对但会翻车的想法）

1. **"注意力尖 → 可以合并相邻 token"** —— 尖度（IPR 4.16）与块内 value 相似度无关；实测块内方差 42–82%。
2. **"块内平均是无损的"** —— 只在 (query, block) 分布上无损，是定义使然；value 侧损失 29–42%。
3. **"用 pool 替代 top-k 就够了"** —— pool 在块粒度无损但块内信息被抹平；剪枝丢质量但保留块内最大值。两者损失不同，不能互相替代。
4. **"压缩率越高越好，反正模型会自适应"** —— 免训练下 m 从 2 到 16，块内偏差从 0.42 涨到 0.82，没有自适应。
5. **"压缩后 KV 缓存就小了"** —— 压缩后要把原 token 丢掉才算省显存；若要能恢复就得留存原件，等于没省。
6. **"只压 prompt 就够了"** —— Gist 类只压提示；"随 token 变多动态压"必须处理生成过程（Activation Beacon 的增量压缩）。
7. **"先训压缩器再说"** —— 在训之前先花一次前向测块内方差（§5），否则可能训了个在 block 内本就不该压的地方用力的模块。

## 9. 追问："token 压缩和 RAG 的 embedding 应该是类似的"

**对了一半，而且对的那一半里藏着唯一有价值的设计结论。**

### 9.1 相同的那一半

两者都是**有损压缩**，都在解同一个形状的问题：

```
min 失真 / max 压缩率   subject to  下游能用
```

都有一个"预算"：RAG 的预算是索引规模/检索 top-k，token 压缩的预算是压缩率。

从**率–失真**视角看，它们是同一条曲线上的两个点：

| | RAG | Token 压缩 |
|---|---|---|
| 编码单元 | 一个 chunk | 一个（或若干）token |
| 存储 | O(语料) 个向量，可离线、可持久 | O(序列) 个向量，**每层都在变** |
| 解码器 | 相似度函数 + 拼回原文 | **transformer 自身** |
| 失真度量 | 检索/问答准确率 | 生成保真度 |

同一份文本，两个目标会训出**完全不同的编码器**——所以它们像，但不可互换。

### 9.2 不同的一半（本质差别）

| | RAG embedding | Token 压缩向量 |
|---|---|---|
| **消费者** | 相似度函数 + 检索器 | transformer 的 KV / 残差流 |
| **目标** | 语义等价（能召回对的段落） | 生成保真度（模型能照着写出来） |
| **粒度** | 一个 chunk → **1 个**向量 | 一个 chunk → **若干**向量 |
| **可检索性** | 它的立身之本 | **从未被优化过** |

最硬的判据：**RAG embedding 喂不进 transformer 的上下文，压缩 token 也检索不出东西**
（下面实测了后半句）。原因不是"尺度不对"，而是**两者的目标函数不同**：
RAG embedding 是**对比学习**训出来的（正负样本、InfoNCE），
它把"语义相同"压到近邻、"语义不同"推开；
压缩 token 是**重构/生成**训出来的，它保留的是"生成下一段需要的信息"。
这两个目标在很多样本上会给出**冲突**的取舍。

### 9.3 实测：压缩表示能当检索索引用吗

脚本 `probe_compression_as_retrieval.py`，48 个块 = 8 话题 × 6 块，
同一份表示既当索引又当查询，测 top-1 同话题检索。随机基线 0.125。

| 表示 | 最佳层 | top-1 | 话题内−话题间间隔 |
|---|---|---|---|
| `last_raw`（最后 token，不压缩） | 26 | 0.1667 | 0.0710 |
| `last_cmp`（最后 token，平均压缩 m=4） | 24 | **0.2083** | 0.0325 |
| `last_ds`（最后 token，剪枝 m=4） | 26 | 0.1250 | 0.0160 |
| `mean_raw`（位置平均，不压缩） | 1 | 0.1042 | 0.0047 |
| `mean_cmp`（位置平均，压缩） | 26 | 0.1458 | 0.0003 |
| `mean_ds`（位置平均，剪枝） | 18 | 0.1250 | 0.0000 |
| **TF-IDF 词法基线**（对照） | — | **0.2083** | 0.0067 |
| 标签打乱负对照 | — | 0.0625 | −0.0011 |

**两个结论**：

1. **压缩本身很稳**：位置平均表示在 m=4 平均压缩后，与不压缩的归一化失真只有
   **0.0499**（剪枝对照是 12.7，差 255 倍）。压缩没有破坏表示结构。
2. **但这个表示本来就不是检索用的**：未训练的隐藏态（无论 last 还是 mean）
   只到 0.17–0.21，**与 TF-IDF 词法基线打平**。也就是说，
   用 LLM 隐藏态建索引并不比词袋好——这恰恰是 RAG embedding 需要**单独训练**的原因。

> 4.3 节测的是 value 向量（m=2 块内偏差 0.42，说明相邻 token 的 value 差异大）；
> 9.3 测的是句级隐藏态（m=4 失真 0.05，说明 chunk 级表示很稳）。
> **两者不矛盾**：块内局部差异大，但块级聚合后稳定。

### 9.4 因此最有价值的设计结论

> **压缩 token 的用途由它的训练目标决定，而这决定了它能不能兼任检索索引。**

- 若压缩向量**只在上下文里用** → 按生成保真度训，**不要**指望它能检索。
- 若想**一个索引同时服务 RAG 与上下文压缩** → 必须在压缩器的目标里
  **显式加一个对齐项**（例如对压缩表示做对比学习/与文本编码器对齐），
  否则你会得到一个"两件事都做不好"的表示——实测已经显示：
  未对齐的隐藏态在检索任务上打不过 TF-IDF。

这是一个**可做、便宜、有明确失败条件**的提案：在压缩器的损失里加
`L = L_lm + λ · L_contrastive(压缩表示, 文本 embedding)`，然后测
(i) 生成保真度掉多少，(ii) 检索能力涨多少，扫 λ 画 Pareto。
这正好补上 §5 那个"块内方差规划"之外的第二个可占的坑。

### 9.5 本次实测的两个方法论坑（都已修）

1. **各向异性**：直接对隐藏态算余弦，48 个块两两相似度全在 0.9966 附近、
   同话题与跨话题间隔恰好 **0**——测试完全无鉴别力。必须去均值/白化。
   这是 LLM 表示作为 embedding 时的已知问题。
2. **没有正面对照就报"表示很弱"是不负责的**：我第一版只跑隐藏态、
   看到 0.17 就想下"压缩破坏语义"的结论。补了 TF-IDF 对照后才知道
   **任务本身就只有 0.21 的天花板**（8 个话题且共享词汇）。
   没有这个对照，我会把"测试设计弱"误读成"压缩有害"。
