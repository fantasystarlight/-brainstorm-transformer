# 把注意力当作有限资源：一次实测 + 三次翻车的记录

> 起因是一句提问："模型运行时注意力矩阵会不断膨胀，如果把注意力当成有限资源去研究限制下的优化方案呢？"
> 这份文档回答两件事：**(1) 这个方向里哪些说法是站得住的、哪些是错的**；
> **(2) 我在这个问题上连错三次的过程**——第二部分比第一部分更有用。

**结论先行（全部为本机实测，Qwen2.5-Math-1.5B-Instruct，T=1024，28 层 × 12 头）**

| # | 结论 | 证据 |
|---|---|---|
| 1 | 注意力极度集中：单个 key 平均占 **45.3%**，位置 0（sink）独占 **36.1%** | Q1 实测 |
| 2 | **均匀稀疏是灾难**：B/T=0.005 时只能捕获 0.05% 的质量，而每行 top-k 能捕获 **64.8%**（差 1264×） | Q2 实测 |
| 3 | **固定滑动窗口不适合这个模型**：去掉 sink 后窗口只覆盖 3–22%；sink+window64 用 65 个 key 才到 **72.9%** | Q4 实测 |
| 4 | 每行 top-k 已经吃掉了几乎全部可达空间：可达最优是"全矩阵 top-B"这个**不可达上界**的 **95–96%** | Q2 实测 |
| 5 | **廉价打分器就够了**：只看"块平均 key"排序（σ=1 噪声）就拿到可达最优的 **93%** | Q3 实测 |
| 6 | 稀疏结构**不跨层复用**：相邻层 top-32 集合的平均 IoU 只有 **0.26** | Q3 实测 |
| 7 | 因此这套预算框架的关键量不是**分配算法**，而是"每层能捕获的质量上限"与"决策成本" | 综合 |

**一句话**：在这个模型上，"把注意力当有限资源做优化"的收益空间**比想象的小得多**——
每行 top-k 已经把 95% 的空间吃掉了，而且用一个几乎免费的打分器就能逼近它；
真正剩下的、值得研究的东西在**别处**（见第 6 节）。

## 0. 先纠正提问里的一个前提

你说"注意力矩阵会不断膨胀"。这句话在三个不同层面成立，而它们的解法完全不同，混在一起谈会得出错误结论。先把它们分开：

| 层面 | 增长方式 | 真正的瓶颈 | 对应资源约束 |
|---|---|---|---|
| **边**：注意力矩阵 \|A\| | 预填阶段 O(T²)，生成阶段每步 +1 行 | FLOPs / 带宽 | 边预算 B = 允许保留的 (query,key) 对数 |
| **列**：KV 缓存 | O(T)（每步 +1 个 key/value 向量） | **显存** | 列预算：能保留多少个不同 key |
| **权**：参数状态 | 不随 T 增长（除非上下文学习） | 与本文无关 | — |

**关键区分（我一开始也糊了）**：边预算 ≠ 列预算。

- 边预算 B 给出的是复杂度上界：每行平均看 k = B/行数 个 key，端到端 FLOPs 从 O(T²) 降到 O(T·k)。
- 但**它不自动带来显存节省**：如果你按值挑 top-k，被访问的 k 个 key 位置是散乱的，
  活跃工作集仍可能触及全部 T 个位置 → 缓存命中率低。实测在本模型上，
  B/T=0.005 时 344,064 个 query 行几乎**每行都触及不同的远端位置**（sink + 远端尾部），
  所以"用边预算省显存"这个推论是错的。
- 反过来，列预算（保留 K 个 key）天然给出显存上界 O(K)，但要在"丢掉哪些 key"上做权衡。

两者是不同的优化问题，**不能互相代替**。下面所有曲线都是**边预算**口径。

## 1. 形式化

设注意力矩阵 `A ∈ R^{L×H×T×T}`（行已归一化），预算 B。

**可达最优（每行 top-k）**

```
maximize   Σ_i  Σ_{j ∈ S_i} A[i,j]
subject to |S_i| ≤ k  for every query row i,   Σ_i |S_i| ≤ B
```

由于**行与行独立**（softmax 按行归一化，掩码也按行给），这个问题的解就是
"每行取自己最大的 k 个"，闭式、无需优化。

**不可达上界（全矩阵 top-B）**

```
maximize   Σ_{(i,j) ∈ S} A[i,j]   subject to  |S| ≤ B
```

它允许"给某行 40 个名额、另一行 3 个"，再把取整损失抹掉，所以**一般严格大于**可达最优。
实测差额只有 1.7–4.7%，来源是 B 不能被行数整除时的取整损失，**不是**结构性空隙。

**曾被我用错的第三个模型（前缀配额）**

```
maximize   Σ_i prefix_i(m_i)   subject to  Σ_i m_i ≤ B
```

含义是"第 i 行想取第 m 名，必须先取它前 m−1 名"——等价于**只能注意最早的 key**。
真实注意力的大权重散布在任意位置（本例：sink 在位置 0，其余质量在距离 >256 的远端），
所以这个模型系统性低估可达性。实测 **64–97% 的行违反该前缀性**（比例随 B 上升）。
它是**另一个问题**，我把它当成了正确模型，见 §5 错误 ③。

## 2. 我实测了六个量

脚本：`attention_budget_probe.py`（一次 fp32 前向 + 纯 numpy 后处理，无训练）。
产物：`docs/attention_budget_probe.json`。图：`docs/attention_budget_dashboard.png`。

| 量 | 含义 | 为什么重要 |
|---|---|---|
| `mean_top1` | 每行最大权重的均值 | 行内集中度：决定"少看几个 key"是否够用 |
| `row_gini` | 行总质量的 Gini | 行间不均衡度：决定"哪些 query 值得多给预算" |
| `col_gini` | 每个 key 被注意总量的 Gini | 列集中度：决定"哪些 key 值得留在缓存" |
| `sink_mass` | 位置 0 独占的质量占比 | sink 现象的量化：决定"固定窗口能不能用" |
| `layer_iou` | 相邻层高权重集合的重叠率 | 决定"分配方案能不能跨层复用" |
| 三条曲线 | 均匀 / 可达最优 / 上界 | 决定"分配算法的收益空间有多大" |

### 实测结果

**Q1 集中度**

```
行内集中：平均 top-1 = 0.4527          ← 一个 key 平均吃掉近一半
行间不均衡：行质量 Gini = 0.0000        ← 恒等！因果 softmax 下行和恒为 1
位置不均衡：列质量 Gini = 0.5680        ← 注意力极不均匀地堆在少数位置上
位置 0 独占质量占比（sink）= 0.3608     ← 超过三分之一
```

⚠ 注意 `row_gini = 0` 是**恒等式**（每行 softmax 和为 1），不是发现。
它的价值在于提醒："行间不均衡"这个说法需要重新定义——行**总量**相同，
不均衡体现在**行间的集中形状**上（有的行全给 sink，有的行分摊）。
这个陷阱我第一次就踩了：float32 噪声还让 Gini 算出 −0.0026 的负值。

**Q2 预算曲线（边预算）**

| B/T | 每行 key 数 k | 均匀稀疏 | **可达最优** | 不可达上界 | 可达/上界 | 廉价打分器 σ=1 | 打分器/可达 |
|---|---|---|---|---|---|---|---|
| 0.005 | 5 | 0.0005 | **0.6476** | 0.6799 | **0.953** | 0.6046 | 0.93 |
| 0.010 | 10 | 0.0017 | **0.7231** | 0.7520 | **0.962** | 0.6821 | 0.94 |
| 0.020 | 20 | 0.0039 | **0.7939** | 0.8216 | **0.966** | 0.7560 | 0.95 |
| 0.050 | 51 | 0.0127 | **0.8782** | 0.9080 | **0.967** | 0.8472 | 0.96 |
| 0.100 | 102 | 0.0298 | **0.9303** | 0.9589 | **0.970** | 0.9075 | 0.98 |
| 0.250 | 256 | 0.0908 | **0.9790** | 0.9957 | **0.983** | 0.9692 | 0.99 |

（`[check]` 行确认：可达最优与"朴素逐行 top-k"的相对差 = 0.00e+00。）

**读法**：均匀稀疏之所以差 1264 倍，是因为"每行给同样多的名额"把预算摊到了
344,064 个行上（每行 5 个），而注意力的质量集中在极少数行-位置对里。
换成"每行 pick 自己的 top-k"这一个动作，就把 0.05% 变成 64.8%。

**Q3 打分器保真度**：把打分器人为加噪 `score = A · exp(σ·noise)`，看捕获质量怎么退化：

| σ | 捕获质量 | 相对可达最优 |
|---|---|---|
| 0（免费 oracle） | 0.794 | 0.966 |
| 0.5 | 0.782 | 0.952 |
| 1.0 | 0.756 | 0.920 |
| 2.0 | 0.677 | 0.824 |
| 4.0 | 0.458 | 0.558 |

**结论**：打分器只要能**大致**排序，就够用了。σ=1（相当于"用块平均 key 近似"这种
粗略程度）还能拿到 92%。这直接推翻了"需要学一个精确的注意力预测器"的直觉。

**Q3 跨层一致性**：相邻层 top-32 集合的平均 IoU = **0.2636**。
低 IoU 意味着**每层都得重新决定**，不能训一个分配器然后所有层共用——
这影响的是部署成本，不是质量上限。

**Q4 简单度阶梯**（改掉掩码 bug 后的数据）

| 模式 | 平均可见 key 数 | 捕获质量 / full |
|---|---|---|
| full（上界） | all | 1.000 |
| only sink | 1 | **0.361** |
| sink + window4 | 5 | 0.524 |
| window4（无 sink） | 4 | 0.167 |
| sink + window16 | 17 | 0.606 |
| window16（无 sink） | 16 | 0.256 |
| sink + window64 | 65 | 0.729 |
| window64（无 sink） | 64 | 0.398 |
| sink + window256 | 257 | 0.860 |
| window256（无 sink） | 256 | 0.597 |

**这张表是整个文档信息量最大的地方**：

- 只看 sink 一个位置就拿到 **36%**。"滑动窗口"类方法**永远看不到它**，
  因为 sink 在序列最开头（StreamingLLM 专门为这件事保留 sink，本机实测复现了该现象）。
- 加上 64 个近邻 key（共 65 个）就到 **73%**，而每行 top-20（共 20 个）的可达最优是
  **82%**。也就是说：**"sink + 局部窗口"这个完全不要打分器的规则，用 3 倍预算换到了
  接近打分器方案的质量**。
- 所以"学一个更好的分配器"能拿到的增量，是在 73%→82% 之间，而不是 0%→82%。

## 3. 由此得到的三个可检验断言

**A1（最重要）**：在这类模型上，稀疏注意力的收益主要来自**保护 sink + 保局部**，
而不是来自**更聪明的 key 选择算法**。
*证据*：Q4 表（规则方案 73%）+ Q3 表（粗糙打分器 92% 可达最优）。
*反证条件*：若在需要长程检索的任务上，"sink+窗口"崩掉而 top-k 保持，
则 A1 不成立——**这是必须做的判决实验**，见 §7。

**A2**：边际价值不在分配算法，而在**每层的质量上限**与**决策成本**。
*证据*：可达最优已经吃满 95–96% 的上界；σ=1 的打分器已拿到 92%。
*推论*：想继续提升，必须动"不是从 A 里挑元素"的手段——重加权、温度、摘要 token、
跨层补偿。**继续在 top-k 分配器上刷分是在一个 3 个百分点的池子里卷。**

**A3**：稀疏结构不跨层、也未必跨步复用（IoU 0.26）。
*推论*：任何"离线学一套稀疏模式再复用"的方案要面对这个数字；
在线方案要为每层付出决策成本。
*未验证*：我这里只测了**预填**阶段的层间 IoU；解码阶段跨步（token-to-token）的可复用性
没测——那才是 KV 淘汰真正作用的地方。**这是本文最大的缺口。**

## 4. 与已有工作的位置关系

> ⚠ 这一节是**二手引用**（来自检索结果与摘要，非全文核对），标注为"据其摘要"。

**同一条河里的工作**：把"注意力/缓存当有限资源"这件事，文献里已经做了很多，
但基本都是在**固定的分配器**上做文章，而不是解约束优化：

- **固定稀疏模式**：滑动窗口、sink+窗口（据其摘要，StreamingLLM 发现保留初始 token 的
  注意力能稳定流式生成）。本文 Q4 表说明：在这类模型上窗口类方案的结构性缺陷是看不见 sink。
- **按值淘汰 KV**：H2O 类方法保留累计注意力高的 token ——**这已经就是"每行 top-k"在列维度的对应物**。
- **自适应预算分配**：Ada-KV 直接研究"按 head 分配不同预算"（据其摘要），
  这正是本文 §1 里"跨行重分配"的那 4% 空间。
- **学出来的稀疏**：SeerAttention 用自蒸馏学一个门控来预测块级注意力（据其摘要），
  对应本文 Q3 的"块平均 key"打分器——**而本文实测这类粗糙打分器已能拿到 92%**。
- **可训练的稀疏注意力**：NSA / MoBA 把稀疏性做进训练目标（据其摘要），
  这是唯一可能突破"95% 可达上限"的路线，因为它改变了模型学到的注意力分布本身。
- **全局组合优化**：有工作把 KV 淘汰表述为带预算约束的组合优化问题求解（据其摘要，
  存在 ICML 2026 的相关工作），与本文 §1 的正式化同源。

**本文相对它们的增量**是三点，且都很小：① 给出了"可达最优 vs 不可达上界"的**实测差额**
（3.7–4.8%，来自取整而非结构）；② 量化了**跨层 IoU = 0.26**；③ 量化了**廉价打分器的
充足性**（σ=1 → 92%）。

**因此我不建议把"更好的分配算法"当课题**。理由：上界只比可达最优高 4%，
而且粗糙打分器已拿到 92%——这两条同时成立时，算法侧的改进空间被夹死了。

## 5. 我在这个问题上连错三次

这一节是本文最有价值的部分。三次错误**全部**是"把一个不可达/不成立的东西当成结论"，
而且全部是我的测试最终抓出来的——每一次抓出来后我都以为"这次对了"，然后又被抓一次。

### 错误 ①：声称"行自适应 water-filling ≡ 全矩阵 top-B"，而实现里把约束假设掉了

我写了个"带前缀约束的贪心"来当参照实现，里面第一步是
`cand = -np.sort(-A, axis=-1)[..., :keep]`——**先把每行候选排序**。
后果：每行的最大元永远排在候选列表第一位，"第 m 名必须先取前 m−1 名"这个约束
在任何输入下都自动满足。于是我的"验证"变成了恒等式：两个东西都是全局 top-B。

**抓出来的方式**：写一个负对照，构造"前缀约束应该绑紧"的数据（第 0 列低价值、
第 1 列高价值、预算只够每行一个名额）。如果实现是对的，带约束的答案应远低于无约束。
结果两者相等 → 说明约束没生效。

**教训**：参照实现里任何"为了让代码简单"的预处理，都可能把被验证的性质消掉。
参照实现必须**笨到显然正确**。

### 错误 ②：穷举参照里的幽灵索引 `pre[i, combo[i]-1]`

为了造上面那个负对照，我写了个穷举：枚举每行取几个（`combo[i]`），算前缀和。
代码是 `pre[i, combo[i]-1]`。当 `combo[i] == 0` 时，Python 的负索引取到**最后一个**元素，
于是给"这一行取 0 个"的分配凭空加上了该行最大的那个值。

后果：穷举结果系统性偏高，**"证明"了前缀约束绑紧**——而这是纯粹的假象。
我在这个假象上又推进了两轮推理。

**抓出来的方式**：手工算一个 3 行 6 列的例子，把每个分配向量的值打印出来，
发现"最优分配"里包含一个 0，却仍然贡献了值。

**教训**：Python 负索引 + 累加 + "取 0 个"这个组合是一个静默的假数据生成器。
涉及"数量为 0"的分支必须显式跳过。

### 错误 ③：把"前缀配额模型"当成正确的可达模型

修完 ② 之后，我相信了"可达最优 = 前缀配额模型"，于是花了很久去实现它的 DP。
但那个模型要求"第 i 行想取第 m 名必须先取前 m−1 名"——**等价于只能注意最早的 key**。
真实注意力的大权重散布在任意位置（sink 在 0，其余在距离 >256 处），
所以这个模型不是在描述注意力，而是在描述另一个问题。

**抓出来的方式**：不再纠结 DP 的算法，而是直接检查一个充要条件——
"全矩阵 top-B 选中的元素，在每个 query 行内是否总是前缀？"
只做排序 + 按行分组，几秒钟出结果：

| B/T | 涉及行数 | 非前缀行数 | 占比 |
|---|---|---|---|
| 0.005 | 169,055 | 107,810 | **63.8%** |
| 0.010 | 171,344 | 143,639 | **83.8%** |
| 0.020 | 171,927 | 161,933 | **94.2%** |
| 0.050 | 172,032 | 167,140 | **97.2%** |

大多数行根本不满足前缀性。**这个模型与现实不符，我白花了半小时实现它的 DP。**

**教训**：在为一个正式化实现复杂求解器之前，先用几秒钟测一个**充要条件**。
如果约束在真实数据上很少绑紧，那它可能根本不是你想要的约束。

### 三次错误的共同形状

| | 我做了什么 | 被什么抓住 |
|---|---|---|
| ① | 预处理消掉了要验证的约束 | 负对照（构造应当绑紧的输入） |
| ② | 穷举里 `pre[i,-1]` 幽灵索引 | 手算一个 3×6 的例子，打印每个候选 |
| ③ | 形式化了错误的约束 | 充要条件的快速可行性检查 |

共同点：**都是"把一个我以为是的前提当成事实"，而三次都不是靠"更仔细地读代码"发现的，
是靠"构造一个应该失败的输入"发现的。**

## 6. 那还剩下什么值得做

按"信息量 × 本机可行性"排序。前两条我觉得是真正空的，后两条是加固。

### P1（推荐）：**"sink 保不保留"的判决实验**

**问题**：sink（位置 0）吃掉 36% 的质量，但这 36% 里有多少是**功能性的**、
多少是 softmax 的"无处可去"（no-op 泄压）？

**已知**：文献里有观点认为 attention sink 可被可学习偏置替代（据其摘要）。
**未知**：在本机这个 1.5B Math 模型上，把 sink 的注意力强行重分配后，
GSM8K/MATH 准确率是否下降。

**做法**（单卡可行，一天量级）：
1. 基线：正常前向，评估 GSM8K（已有缓存）。
2. 干预 A：把位置 0 的注意力权重置零后重新归一化（等价于"禁止泄压"）。
3. 干预 B：把 sink 质量重分配给最近的 k 个 token。
4. 干预 C：换成可学习 sink 偏置（需要微调，成本高，可选）。

**判据**：若 A/B 准确率相对基线下降 < 1 个百分点 → sink 是 no-op，可安全省略，
这直接支撑"固定 window 方案"的可行性；若崩掉 → sink 是功能性的，
所有不保护 sink 的稀疏方案都有系统性缺陷。

**为什么值得做**：这个实验的结论会**翻转** §3 的 A1，而它只要一次前向 + 一次评估。

### P2：**预算耗尽与"并发检索容量"的关系**

**问题**：如果每层每行只有 k 个名额，那"模型能同时处理几件事"是否就受限于 k？

**假设**：在多针检索（needle-in-haystack）任务上，针数 N 超过某个阈值后准确率崩塌，
且阈值与每层可用边预算单调相关；而"顺序推理"（需要同一份信息被多次回看）比"并行检索"
对预算更敏感，因为它需要在多层里反复命中同一个 key。

**做法**：
1. 构造 N 针检索任务，N = 1..32，位置随机，T 固定 4096。
2. 分别在 full attention / 每行 top-k (k=8,16,32) / sink+窗口 下评估准确率。
3. 画 N–准确率曲线，比较崩塌点。

**判据**：若 top-k 的崩塌点显著晚于 sink+窗口，说明"远端正位置"对多跳任务必要，
A1 需要修正；若两者崩塌点接近，A1 加强。

**为什么值得做**：这把"注意力预算"从一个效率参数变成**能力上限参数**，
是唯一可能产出"有意思的结论"而不是"又一个稀疏化方法"的方向。

### P3：**解码阶段的可复用性**（补本文最大的缺口）

本文只测了预填阶段的层间 IoU（0.26）。KV 淘汰真正作用在**解码**阶段：
第 t 步的保留集合，在第 t+1 步还有效吗？

**做法**：跑一次长生成（1024 token），逐层逐步记录 top-K 集合，算
(i) 相邻步 IoU，(ii) 间隔 8/32/128 步的 IoU 衰减曲线。
**判据**：若 IoU 随步数快速衰减 → 淘汰策略必须在线重算；若缓慢 →
可以离线学一个稳定的保留策略（这类工作已有，但本机没测过）。

### P4（加固）：**决策成本的公平记账**

几乎所有稀疏注意力论文都报"质量 vs 稀疏度"，很少报"打分器的算力/带宽成本"。
本文 Q3 显示粗糙打分器就够用，但**没测打分器本身的成本**。

**做法**：在同一个 kernel 里实现三档打分器（块平均 key / 无打分器规则 / 精确），
在同一 batch 上测实际 latency，然后画**端到端**的 Pareto（质量 vs 总时间），
而不是"质量 vs 理论 FLOPs"。本机 4080 上可做，需要写 CUDA 或至少 triton kernel。

## 8. 方法论护栏（本次新加的）

1. **参照实现必须笨到显然正确**：任何"为了让代码简单"的预处理都可能把被验证的性质消掉（错误 ①）。
2. **涉及"数量为 0"的分支必须显式跳过**：Python 负索引 + 累加是静默的假数据生成器（错误 ②）。
3. **为正式化实现复杂求解器之前，先用几秒测一个充要条件**（错误 ③）。
   *本次的具体产物*：`docs/` 里的可行性检查（top-B 选中的元素在行内是否前缀），
   4 个预算点、每点几秒，直接否掉了我花了半小时实现的模型。
4. **负对照要能真的失败**：我写的第一个负对照（把行改成升序）是废的——
   降序/升序只是行内置换，约束在两种情况下都不绑紧。
   有效的负对照必须让"元素顺序"与"价值顺序"冲突。
5. **别在不可达的上界上做优化**：本文三次里有两次是在优化一个不存在的东西。
6. **实测数字与估算分开写**：本文所有数字都是本机实测；引用的文献结论标为"据其摘要"。

## 附录：第 4 个坑（补记）

修完错误 ③ 之后我写验证器时又踩了一次，值得单列，因为它和前三个不同类：

**错误 ④：验证器复刻了"意图"而不是"契约"。**

`row_topk_optimum` 的名额分配是 **ceil** 语义——`k = ceil(B/行数)`，
只有 `行数 − rem` 行拿到 k 个（前 rem 行少 1 个）。
我的验证器按 **floor** 语义写——`k = floor(B/行数)`，前 rem 行**多** 1 个。
两者差"每行多拿一个"，于是验证器报出 8e-10 的相对差。

我当时的第一个反应是"这是 float32/float64 累加顺序误差，把容差从 1e-12 放宽到 1e-6 就行"——
**这个反应是错的**，而且很危险：它会把一个真实的契约不一致当成数值噪声掩盖掉。
真正发现它是因为我把容差放宽后测试仍然红（相对差其实是因为 k 差 1，不是浮点）。

**教训**：验证器与被验证者的**接口契约**必须逐字一致（包括取整方向、边界归属、
"余额给谁"）。浮点容差只能吸收**同一算法的不同累加顺序**，不能吸收**不同的离散决策**。
区分二者的办法：看差异的大小是否与输入规模相关——累加误差随规模缓慢增长（1e-10 量级），
而取整方向差异是结构性的（会直接改变若干个元素）。

  gini(x)：注意行和为 1 时恒等于 0，别当发现
